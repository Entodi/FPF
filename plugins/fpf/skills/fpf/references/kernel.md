# FPF Kernel — Non-negotiable Ideas

These ideas are normative across every FPF skill. If a draft violates them, fix the draft, not the rule.

## The seven core ideas

1. **Local meaning, explicit translation.** Terms live inside bounded contexts (local working frames with their own meanings). Cross-context reuse is never obvious; it needs an explicit bridge.
2. **One underlying reality, many aligned outputs.** Engineering, management, research, and assurance outputs are projections of the same underlying work — not disconnected documents.
3. **Separate systems, roles, method descriptions, methods, plans, and executed work.** Descriptions, capabilities, plans, and actual occurrences are different things. The transformer quartet enforces this separation.
4. **Trust has structure and grounding.** A claim should say how formal it is (F), where it applies (G), what evidence supports it (R), and which carriers or systems anchor it.
5. **Composition matters across scales.** The same logic should survive when parts aggregate into wholes.
6. **Keep search wide before selection.** In open-ended work, diversity of options matters before picking a winner. Premature convergence is a category-3 failure.
7. **Build from first principles when categories break.** FPF is not only for organizing the current state of the art; it is also for growing new abstractions when local folklore is misleading.

## What FPF buys you (after one pass)

A first practical pass should stabilize concrete artifacts — not just better intuition:

- a map of bounded contexts and responsibility boundaries;
- explicit decision criteria and trade-off characteristics;
- a small portfolio of alternatives instead of premature convergence;
- a visible evidence / test gap list before commitment;
- a starter DRR (Decision Rationale Record);
- a starter UTS (Unified Term Sheet);
- aligned outputs for engineering, management, research, and assurance.

## When to reach for FPF

Use FPF when several of these are true:

- work is split across specialised people, teams, copilots, or AI agents;
- the real-world oracle is delayed, noisy, expensive, or risky;
- different audiences need aligned outputs from the same underlying work;
- trade-offs between speed, quality, risk, novelty, and compliance must be explicit, not hidden in one opaque score;
- existing categories are breaking down and you need to grow new concepts from first principles.

## When FPF is overkill

- the task is small;
- vocabulary is already stable;
- feedback is fast and cheap;
- the cost of semantic drift is low;
- no durable shared reasoning form is needed;
- you mainly need a quick answer, not a reusable reasoning form.

## Three modes of use

1. **Human-only.** FPF as a reading, writing, and review discipline with no AI in the loop.
2. **Mixed team.** FPF as a coordination layer across people, copilots, and AI agents — where local working frames, responsibility boundaries, and audience-specific outputs matter most.
3. **AI assistant.** FPF loaded as an attached file or indexed reference; the assistant uses it as a reasoning scaffold.

## What FPF is not

- not a shrink-wrapped methodology like Agile or Waterfall;
- not a quick-answer cheat sheet;
- not a demand to read the whole specification linearly before doing useful work;
- not a substitute for good problem framing — without good questions, FPF will help you produce well-structured nonsense.
